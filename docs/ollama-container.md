# Containerized Nomic embeddings

Run the existing application startup command from the project root:

```powershell
docker compose up -d --build
```

No separate Ollama installation or manual model pull is needed. Docker with Linux
containers, sufficient RAM/disk, and internet for the first image/model download
are still required. The official image can be several GB, so the first download
may take a while on slower connections. The image supports Linux AMD64 and ARM64; the default
uses CPU execution and does not require GPU drivers. External integrations still
need their existing root `.env` credentials. This is not a zero-configuration
replacement for Gemini, Google Forms, Discord, SMTP, LiveKit or Deepgram setup.

## Startup flow

1. `ollama` starts the pinned official image with a private API on port 11434.
2. `ollama-init` waits for its health check, checks the local model inventory and
   downloads `nomic-embed-text:latest` only if missing. The download is about 274 MB,
   in addition to the container image. Network/download failure leaves setup failed.
3. Initialization verifies the expected model digest, produces one synthetic
   embedding, validates that it is finite/nonzero and 768-dimensional, and checks
   that the digest did not change during inference. No candidate text is used.
4. Only after successful initialization does Compose start the backend. Both
   knowledge retrieval and CV evidence retrieval use `http://ollama:11434`.

The Nomic alias, digest, search prefixes and vector dimensions are preserved.
Existing database vectors are not deleted or regenerated by this change. A
different model digest stops setup rather than silently accepting incompatible
vectors. The Ollama engine image is also pinned by version and multi-platform
manifest digest. Engine/model upgrades should be deliberate and verified.

The persistent `ollama_data` named volume stores models across restarts. With the
image and model already cached, setup skips the remote pull and can succeed
without registry access. Running container health checks never download a model.
The embedding API has no published host port and cannot be reached through the
website tunnel. Only application credentials go to the backend; the model setup
job receives no database, application-document or external-provider credentials.
Its lightweight, non-root image contains only Python and the setup script, not
the backend's application dependencies or candidate storage.

Compose deliberately ignores legacy `OLLAMA_DOCKER_BASE_URL` values, so an old
root `.env` pointing to `host.docker.internal` cannot bypass the container.
`OLLAMA_BASE_URL` in the root file remains a setting for non-Docker backend
development only. Neither the root `.env` nor host Ollama models are modified.

## Checks and recovery

```powershell
docker compose ps -a ollama ollama-init backend
docker compose logs --tail 30 ollama-init
docker compose exec ollama ollama list
```

An exited initializer with status **0** is expected; it is a one-shot setup job.
After a failed download, fix connectivity/disk space and run
`docker compose up -d --build` again. Compose will retry the job; successful cached
models are reused. A digest mismatch requires investigation, not disabling the
check. Changing the model requires a safe re-embedding plan for **both** knowledge
chunks and CV passages, even if the replacement also produces 768 dimensions.

For an already-running installation, finish active interviews and processing
jobs before recreating the backend. Prepare `ollama` and `ollama-init` first, then
recreate the backend while preserving its existing public-origin overlay. Do not
restart the tunnel or change invitation links just to migrate embeddings.

`docker compose down` retains both `postgres_data` and `ollama_data`. Do **not**
use `down -v` unless deliberately deleting all named-volume data, including the
database and downloaded models. No volume deletion is needed for this migration.
