# New application notifications

The interviewer navigation bar has a bell badge for Google Form responses that have not yet been imported. The popover shows counts per posting, plus a separate warning/count for missing, unknown or ambiguous job selections. **Review and sync** opens Candidates, where the interviewer can use the existing sync button or central assistant. Viewing notifications does not clear the badge, import candidates, download CVs or start screening.

The frontend checks on opening the app, about once a minute while visible, and when returning to the tab. Checks pause in hidden tabs. Manual and conversational syncs trigger an immediate count refresh; database reconciliation is fresh even if the source-sheet snapshot is cached. This is an in-app pending-response indicator, not email, OS/browser push, or a background notification while the app is closed.

`GET /api/candidates/notifications` requires an active interviewer JWT and returns only aggregate counts, owned posting titles/IDs and the last sheet-check time. Candidate accounts cannot access it. Responses are `no-store`. It reuses the configured Google response spreadsheet, tab, headers and job-routing rules. Only Sheets is read; Drive files, the Google Form and the business database are not changed. Sheets reads have a 15-second transport timeout. Missing configuration and failed checks are shown as unavailable, not a false zero count.

Snapshots and failed-check cooldowns are cached in process for 60 seconds, scoped by interviewer and source sheet, with at most 32 entries. Concurrent checks share a refresh. Current imported references, legacy imported row metadata and deliberate-deletion exclusions are checked each time. Exact duplicate responses, blank rows and rows without a usable name/email are not counted. The stable-reference and row-metadata behavior matches the existing importer; already imported rows edited in Sheets are not counted as new applications. Counts represent applications, not unique people: one person applying to two jobs can count twice.

The configured form must retain the required Job Posting field. Correct routing issues in the response sheet before syncing; the notification never guesses which job the candidate intended. Invalid routing rows contribute to the badge but are listed separately from applications ready to sync. Already collected applications with a missing CV are not new responses and are not counted here; retry their existing sync/download flow instead.

No schema migration, new credentials, Google Form edits or environment variables are needed. Existing read-only service-account access is reused. This single-process cache is suitable for the current deployment; multiple backend replicas would need a shared cache/rate limit to deduplicate API reads across replicas.
